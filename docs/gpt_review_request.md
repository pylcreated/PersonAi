## 二、项目定位

Personal Agent 是一个运行在 Windows 个人电脑上的本地、单用户、隐私优先
个人智能体。

它不是通用聊天机器人，而是围绕个人目标和日常行动建立持续闭环：

```text
长期目标
  → 每周任务
  → 当天实时对话
  → 次日结构化分析
  → 用户审核长期记忆
  → 后续对话和行动规划
```

当前使用 Python、SQLite 和本地 Ollama 模型。默认模型为
`gemma3:12b`，不依赖付费 API，不接入邮件、Telegram 或其他外部消息渠道。

项目目前处于 MVP 到可持续自用版本之间：核心链路和架构骨架已经完成，
但真实交互体验、数据迁移、长对话处理和真实模型质量仍需继续验证。

## 三、核心功能

### 1. 实时对话

- 用户通过本地 CLI 与 Agent 连续聊天。
- 每轮保存用户消息和助手回复。
- 回复上下文包含当天聊天、长期目标、本周任务、近期日报和相关长期记忆。
- Ollama 不可用时返回明确错误，不让程序直接崩溃。

### 2. 每日分析与聊天清理

- 原始聊天按照北京时间自然日保存。
- 每天 `00:05` 分析前一天聊天。
- 分析生成总结、进展、阻碍、模式、状态和下一步行动。
- 日报成功保存后，自动删除对应日期的原始聊天。
- 日报保存、候选记忆保存和聊天删除位于同一数据库事务。
- 如果模型、JSON 校验或数据库写入失败，原始聊天不会删除。
- 失败任务每 30 分钟重试；程序重新启动时也会补做历史分析。

因此，“只保留一天”是正常情况下的目标；发生分析失败时，系统优先避免
数据丢失，原始聊天可能临时保留更久。

### 3. 用户可控长期记忆

长期记忆分为两个阶段：

```text
每日分析提出候选
  → 用户查看、编辑、接受或拒绝
  → 接受后成为正式记忆
```

- 模型不能直接写入正式长期记忆。
- 候选和正式记忆物理分离。
- 正式记忆支持状态管理和软删除。
- 接受候选前进行保守的冲突检测。
- 只有用户确认且处于 `active` 状态的相关记忆才能进入对话上下文。
- 当前记忆类型包括 profile、preference、goal、project、skill 和
  experience。

### 4. 目标与任务

- 创建和查看长期目标。
- 为目标新增每周任务。
- 查看、完成和重新打开任务。
- 日报与周报可结合目标和任务数据。

目前目标和任务的编辑、删除、优先级、截止日期等管理能力还不完整。

### 5. Tool 与 Permission

当前实现了受控的本地文件工具：

- 读取和搜索文件。
- 创建文件。
- 显示 diff 后更新文件。
- 更新前保存旧版本。
- 删除文件时移动到回收区。
- 恢复被回收文件。
- 在部分文本格式之间转换。

安全规则：

- 工具只能通过 `ToolManager` 执行。
- 工作区外默认拒绝写入。
- 删除、执行等危险操作必须逐次确认。
- 路径规范化后再次检查，防止目录穿越。
- Agent 内部状态、审计、备份和回收目录不能被普通工具修改。
- 工具调用只记录必要元数据，不把文件正文写入审计日志。

### 6. Agent Orchestrator

当前调度流程：

```text
用户任务
  → LLM Planner 生成有限 JSON 计划
  → 本地规则验证工具、参数和风险
  → 用户审核计划
  → Executor 按顺序调用 ToolManager
  → 保存任务和步骤状态
```

安全边界：

- 计划最多 8 步。
- Planner 只能选择已注册工具。
- 工具参数必须符合 Schema。
- 风险等级由本地规则最终决定。
- 用户拒绝后零执行。
- 第一个步骤失败后停止后续步骤。
- 当前不会自动重新规划，也不会自行扩大已审核计划。

## 四、当前架构

正式源码全部位于 `personal_agent/`：

```text
personal_agent/
├── __main__.py          # 正式入口
├── bootstrap.py         # 唯一依赖组装位置
├── agent/               # Planner、审核、执行、状态和风险
├── application/         # 调度、重试和启动补偿
├── core/                # 对话 Agent、上下文和抽象端口
├── analysis/            # 日报与周报用例
├── memory/              # 记忆、检索、生命周期、仓储和 SQLite
├── llm/                 # LLM 接口及 Ollama 等适配器
├── tools/               # 工具协议、注册与统一执行
├── security/            # 权限与审计
├── interfaces/          # CLI 和本地输出
└── config/              # 配置读取
```

设计原则：

- 核心逻辑不知道具体使用 Ollama 还是其他模型。
- 核心逻辑不知道数据具体保存在 SQLite。
- 分析层不直接执行 SQL 或操作 CLI。
- Tool 不自行决定权限。
- 具体实现只在 `bootstrap.py` 中组装。
- 旧入口已经迁入 `legacy/`，正式代码没有旧模块引用。

## 五、数据与隐私

- 数据保存在本地 SQLite：
  `data/database/goals_assistant.db`。
- `.env`、数据库、日志和运行状态不进入版本控制。
- 使用本地 Ollama 时，对话不发送到云端。
- 自动化测试使用隔离的内存数据库，不修改真实数据。
- 原始聊天在日报成功后删除，长期只保留结构化日报和用户确认的记忆。

当前尚未完成：

- JSON/Markdown 数据导出。
- SQLite 加密。
- 用户主动导出或彻底遗忘指定数据。
- 日报版本、提示词版本和重生成记录。

当前已经完成：

- 三段 SQLite schema migration 和失败回滚。
- 日报后备份、每天 `00:30` 兜底备份、最近 30 份保留及安全恢复。
- 日报 Evidence 原文校验。
- 正式记忆的来源、创建原因和 Evidence 追踪。

## 七、当前最明显的产品与技术问题

1. CLI 是唯一界面，普通用户操作成本较高。
2. `gemma3:12b` 首次加载较慢，目前没有流式输出。
3. 实时聊天和日报使用同一个模型，尚未按任务分配不同模型。
4. 每日分析会一次提交当天全部聊天，超长聊天可能超过上下文。
5. 日报目前主要验证 JSON 结构，无法自动判断事实遗漏和幻觉。
6. 凌晨分析与仍在进行的跨日回复之间缺少明确的会话锁。
7. 最早失败日期可能阻塞后续日期的分析。
8. 数据库没有正式迁移、自动备份和恢复机制。
9. 长期日报只按最近天数进入上下文，没有月度或主题级压缩。
10. Agent 的计划是静态计划，不能根据工具结果安全地生成下一阶段计划。
11. 目标和任务管理仍缺少编辑、停用、优先级和截止日期等常用能力。
12. 目前还缺少一段持续真实使用数据来验证这个产品是否真的改善行动。

## 八、项目约束

请在建议中遵守：

- 优先本地运行、免费和隐私。
- 当前主要环境是 Windows、约 16 GB 内存、RTX 4060 Laptop。
- 暂时不接入付费 DeepSeek API。
- 暂时不开发邮件、Telegram、多人权限和云端同步。
- 暂时不引入微服务、消息队列或复杂分布式架构。
- 可以继续使用 SQLite。
- 每日分析成功后仍应删除原始聊天。
- 危险工具必须由用户审核，不能为了“更智能”而降低安全边界。
- 后续设计应适合个人项目逐步实现，而不是按大型团队方案规划。
