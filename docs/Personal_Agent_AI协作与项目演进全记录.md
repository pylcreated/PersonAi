## 一、项目起点：目标驱动的主动教练

项目最初被定义为“个人 AI 目标复盘教练”，更长期的愿景是个人 AI
操作系统。它关注的不是一次性问答，而是用户长期目标、每日行动和持续反思。

最初设想的闭环是：

```text
感知状态
  ↓
生成反思问题
  ↓
收集用户回复
  ↓
更新目标与计划
  ↓
进入下一轮
```

与普通待办清单或笔记软件相比，这个设想强调三点：

- 主动性：系统会定时提问，而不是等待用户想起记录。
- 连续性：历史信息会影响下一次提问和建议。
- 方向性：任务服务于长期目标，而不只是堆积零散事项。

DeepSeek 在第一轮总结中把项目的差异化概括为“目标驱动的主动反思代理”。
从产品价值看，它试图降低日常记录成本，让用户在真实使用中逐渐形成目标、
行动、反馈和复盘的循环。

## 二、第一版方案：Telegram + OpenAI + SQLite

### 2.1 初始技术方案

第一轮提示词把项目限定为一个简洁 MVP：

- Python 3.11。
- `python-telegram-bot`。
- SQLite。
- OpenAI API。
- `python-dotenv` 与定时调度。

初始数据模型包含：

- `goals`：长期目标。
- `tasks`：目标对应的每周任务。
- `reflections`：每日问题、用户回答和 AI 摘要。

初始交互流程是：

1. 用户通过 `/start` 进入初始化。
2. 输入 1～3 个长期目标。
3. 设置每日提醒时间。
4. Bot 每天按目标提问。
5. 用户回答后写入 SQLite。
6. 周日调用 LLM 生成进展、阻碍和下周计划。
7. 用户确认后更新下一周任务。

这一阶段明确“不做 Web/App UI、不做多用户、不做向量数据库”，目的是先
验证主动复盘是否真的有价值。

### 2.2 第一轮开发方式

用户把大需求拆成多个连续提示词：

- 初始化依赖、`.env.example` 和配置模块。
- 设计 SQLite 存储层。
- 创建 Telegram Bot 骨架。
- 增加每日定时提问。
- 生成 LLM 周报。
- 实现初始化状态机。
- 增加周报确认和任务更新。

这种“小步快跑、每次只做一个可测试增量”的方式，成为后续 AI 协作的
基础方法。

## 三、第一次现实碰撞：代码能跑，但产品没有活起来

VS Code Agent 的实际启动反馈暴露了第一个阻塞问题：

- Python 依赖已经安装。
- 代码可以进入 Bot 初始化阶段。
- 启动被无效或缺失的 Telegram Token 阻塞。
- OpenAI Key 和账户可用性同样是外部依赖。

这次反馈的重要意义是区分了两类问题：

```text
代码问题：语法、导入、业务逻辑错误
运行问题：Token、Key、余额、网络和外部服务
```

Agent 判断当时的项目已经有较完整的 MVP 骨架，但还没有完成真实 Telegram
端到端验证。DeepSeek 随后给出 P0/P1/P2 修复清单：

- P0：配置 Token、加载 `.env`、验证 LLM Key。
- P1：真实走通初始化、定时任务和周报链路。
- P2：改善帮助、错误提示、重复启动和输入引导。

这个阶段形成了一个重要认识：

> “代码完成”不等于“产品可用”；能否稳定启动、完成真实交互并保存数据，
> 才是 MVP 的验收标准。

## 四、消息通道的调整：从外部平台走向本地

### 4.1 为什么放弃 Telegram

Telegram 方案需要 BotFather、真实 Token、网络连接和外部平台可用性。
对于一个只供个人使用的本地项目，这些成本反而阻碍了核心闭环验证。

DeepSeek 曾比较邮件、企业微信、个人微信、钉钉和飞书，并一度建议用邮件
作为低门槛替代。邮件方案虽然减少平台注册难度，但仍然需要 SMTP、IMAP、
授权码、收件箱轮询和网络稳定性。

### 4.2 最终转向本地控制台

后续 Agent 反馈显示，项目最终把消息通道改造成了本地控制台会话：

- 不再依赖 Telegram 或邮箱。
- `LocalChannel` 负责本地消息。
- 模型层改为兼容 OpenAI 风格接口，并支持 DeepSeek。
- Mock 模式允许在没有真实 API 时验证业务链路。

这一变化保留了目标、任务、日报和周报逻辑，同时移除了最影响自用验证的
外部通道依赖。

### 4.3 再次本地化：Ollama

随着项目继续演进，模型也从外部 API 转向本地 Ollama，默认使用
`gemma3:12b`。这使系统进一步满足：

- 不依赖付费 API。
- 原始数据留在本机。
- 模型配置可以在本地切换。
- 测试不依赖网络。

代价是本地模型生成速度受硬件影响，长回答、周回顾和每日分析可能需要更长
时间。用户明确选择继续使用大模型，而不是用规则或假数据替代生成质量。

## 五、从 MVP 脚本到分层 Personal Agent

项目逐步从根目录脚本迁移为 `personal_agent/` 分层结构：

```text
personal_agent/
  agent/         有限计划、风险、审核、执行
  analysis/      日报和周报
  application/   调度与工作流
  config/        运行配置
  core/          对话、上下文和 ChatToolRunner
  interfaces/    CLI、LocalChannel、Web/API
  llm/           Ollama 和兼容接口
  memory/        SQLite、日报、Evidence、候选和备份
  security/      Permission 与 Audit
  tools/         文件 Tool 和应用 Tool
```

旧代码移到 `legacy/`，正式业务逻辑只从 `personal_agent` 导入。

架构遵循以下依赖方向：

```text
入口
  ↓
bootstrap
  ↓
interfaces / application
  ↓
agent / core / analysis
  ↓
LLM、Repository、Tool、Permission 抽象
  ↓
Ollama / SQLite / 本地文件系统
```

这个阶段的目标不再只是“增加功能”，而是避免模型、数据库、界面和业务逻辑
互相缠绕，为后续 Web UI 和 Tool 调用留下清晰边界。

## 六、数据可靠性：日报、Evidence 与长期记忆

### 6.1 每日摘要不只是模型作文

系统设计为次日处理前一天聊天，生成：

- 摘要。
- 进展。
- 模式。
- 情绪。
- 下一步行动。
- 可信度。
- 最小 Evidence。

日报中的 `progress`、`obstacles` 和 `next_actions` 必须由真实用户消息
支持。Evidence 保存原消息 ID、时间和逐字片段。

日报、Evidence、候选记忆和聊天清理位于同一事务。如果模型输出、证据校验
或数据库写入失败，事务回滚，原始聊天继续保留。

### 6.2 用户控制长期记忆

模型只能提出候选记忆，不能直接写入正式长期记忆。用户可以：

- 查看候选。
- 查看来源日期和 Evidence。
- 接受候选。
- 忽略候选。
- 在 CLI 中编辑、归档、过期或软删除记忆。

只有用户确认且状态为 `active` 的记忆才会进入后续对话上下文。

### 6.3 从“记忆页面没作用”到完整审核链路

在 UI 迭代中，用户多次指出：

- 前一天有聊天，但页面没有出现候选记忆。
- 无法查看已保存的长期记忆。
- “记忆审核”只有空页面，没有关键操作。

最终联动包括：

- Dashboard 返回每日摘要、待审核候选和正式记忆。
- 页面展示未分析日期。
- 用户可以补做未处理聊天分析。
- 接受或拒绝候选后自动刷新。
- 已确认记忆单独展示。

系统同时澄清一个重要语义：日报已经生成但候选列表为空，不一定是错误，也
可能表示模型没有发现值得跨天保留的信息。

## 七、Web UI：从参考图到真实产品界面

### 7.1 UI 目标

用户提供了一张“个人 AI 助手”参考图，希望界面安静、可信，而不是常见的
通用聊天产品。最终 UI 包含：

- 今日。
- 对话。
- 目标与任务。
- 回顾。
- 记忆。
- 设置。

视觉上采用左侧导航、卡片式 Dashboard、紫色主色、柔和背景和本地状态提示。

### 7.2 启动脚本的多轮修复

最初的一键脚本出现中文批处理乱码、命令被拆分和端口不一致。用户明确提出：

1. 一个脚本负责启动项目。
2. 一个脚本负责打开 UI。
3. 两个脚本必须真正连接前后端。

最终形成：

- `启动项目.bat`：检查环境和端口，启动后端及 Web API。
- `打开UI界面.bat`：检查健康接口，必要时自动启动后端，再打开浏览器。
- 默认端口统一为 `8765`。
- 健康检查要求 `service=personal-agent` 且 `api_version=7`。

同时删除了错误的 `python -m http.server 8080` 文档说明。独立静态服务器
只能打开页面，不能提供 `/api/*`，这正是早期 `501` 和“本地服务连接失败”
的来源之一。

### 7.3 从“假按钮”到真实联动

用户逐项点击页面并指出不能使用的区域：

- 开始对话与智能对话入口重复。
- 任务“更多”按钮无响应。
- 管理任务、完整日报、本周进度按钮无响应。
- 生成本周回顾速度慢或无法生成。
- 添加目标、添加任务、设置和备份按钮只是样式。

这些反馈推动前端从静态原型改为真实 API 客户端。当前主要接口包括：

- `/api/dashboard`
- `/api/chat`
- `/api/goals`
- `/api/tasks`
- `/api/daily`
- `/api/weekly`
- `/api/memory/analyze`
- `/api/memories/{id}/accept|reject`
- `/api/settings/model`
- `/api/settings/reminder`
- `/api/backups`

### 7.4 对话体验修正

用户指出聊天气泡宽度不稳定、用户和 AI 没有分列、返回页面时总停在顶部。
最终调整为：

- 用户消息靠右，AI 消息靠左。
- 气泡宽度随内容变化但保持最大宽度。
- Enter 发送，Shift+Enter 换行。
- 发送后显示“处理中”状态。
- 返回聊天页面默认滚动到最新消息。

## 八、任务模型：长期方向与个人清单分离

早期设计把所有任务都强制关联长期目标。用户后来明确指出：

> 用户应该自己添加今天或本周任务；任务清单不必全部属于长期目标。

因此新增 `personal_tasks`：

- `scope=day` 表示今天任务。
- `scope=week` 表示本周任务。
- 今天任务保存具体日期。
- 本周任务保存周起始日期。

长期目标继续表示方向，任务清单负责行动。聊天 Tool 仍可以在用户明确要求时
向某个目标添加目标任务，两种模式并存。

## 九、关键转折：模型必须调用 Tool 真正执行

### 9.1 问题

用户曾要求模型把七个学习任务加入系统。模型回复“已经添加”，但 UI 没有
出现对应任务，之后还出现中文乱码。

这暴露出一个关键问题：

```text
模型说“已完成”
≠
数据库真的发生变化
```

### 9.2 用户的明确需求

用户最终把要求表述得非常清楚：

> 我给大模型的指令，它可以通过调用 Tool 进行操作。

### 9.3 解决方案

系统增加 `ChatToolRunner` 和应用 Tool 白名单：

- `list_goals`
- `list_tasks`
- `create_goal`
- `add_goal_task`
- `set_task_completed`

处理流程变为：

```text
用户操作指令
  ↓
ChatToolRunner 判断是否需要 Tool
  ↓
Planner 从白名单生成计划
  ↓
ToolManager 校验、执行、审计
  ↓
数据库真实更新
  ↓
聊天返回逐步执行结果
  ↓
UI 重新加载 Dashboard
```

如果计划无效或某一步失败，回复会明确说明没有修改或在哪里停止，不再用普通
对话文本冒充执行结果。

这一改变把项目从“会聊天的界面”推进成了真正能够改变系统状态的 Agent。

## 十、设置与模型状态

用户发现设置页显示“local·未配置”，与实际已经接入大模型矛盾，并指出模型、
提醒和备份按钮不可用。

最终 Dashboard 返回真实模型信息：

- provider：`ollama`
- model：`gemma3:12b`

设置页连接后端：

- 保存模型名称，重启后生效。
- 修改每日提醒小时。
- 查看并创建 SQLite 备份。

这解决了“聊天能回复，但设置页说未配置”的状态分裂。

## 十一、前后端联调结果

前端使用同源相对路径 `/api/*`，后端同时提供静态 UI 和业务 API，默认地址：

```text
http://127.0.0.1:8765
```

实际联调确认：

- `/api/health` 返回 200，API 版本 7。
- `/api/dashboard` 返回目标、任务、消息、摘要、候选、记忆、设置和模型。
- `/api/daily`、`/api/backups` 正常。
- `/`、`/app.js` 正常提供 UTF-8 静态资源。
- 无效目标、任务、提醒和记忆操作返回明确 400。
- 错误输入不会改变真实目标、任务或候选数量。
- 前端所有 `getElementById` 都能在 HTML 中找到对应节点。
- 前端请求路径都有后端路由。

自动化测试结果：

```text
84 passed
0 failed
```

JavaScript 语法检查也已通过。

当前测试缺口是：pytest 尚未直接启动临时 HTTP 服务验证全部 API 状态码与
响应 Schema，实时接口契约仍主要依赖联调检查。

### 12.2 认证问题

用户最初在 WSL 中安装 GitHub CLI，通过设备码登录时遇到：

- WSL 无法自动打开 Windows 浏览器。

`gh auth status` 确认账号 `pylcreated` 已登录。

`127.0.0.1:7890` 完成推送。

- 创建 `.gitignore`。

- 运行 84 项测试。

## 十四、AI 协作方法总结

### 14.1 有效做法

本项目中最有效的协作方式不是一次性要求 AI “做完整项目”，而是：

1. 先给出清晰的产品目标。
2. 把功能拆成可以运行的小步骤。
3. 每一步都实际启动和点击。
4. 用截图和具体位置反馈问题。
5. 区分“视觉完成”“接口完成”和“数据真的变化”。
6. 让 AI 在修改后运行测试和联调。
7. 重要架构决策写入文档和 Git。

### 14.2 用户反馈的价值

本轮大量关键改进都来自非常具体的使用反馈：

- “两个脚本都有问题。”
- “按钮无法点击。”
- “本地服务没有连接。”
- “任务没有添加或联动。”
- “我要的是模型调用 Tool 进行操作。”
- “返回聊天页面应该默认在最底端。”

这些反馈比抽象的“优化体验”更有效，因为它们提供了可定位的页面元素、错误
状态和预期行为。

### 14.3 AI 输出必须验证

项目多次证明：

- 代码生成后要实际运行。
- 按钮存在不代表功能存在。
- 模型回复成功不代表数据库成功。
- 浏览器授权成功不代表终端状态已经更新。
- 单元测试通过不代表 HTTP 接口一定匹配。
- 文档写着某个端口不代表启动脚本也使用同一端口。

因此最终形成“实现—运行—观察—修复—测试—文档—提交”的闭环。

## 十五、当前项目状态

当前项目已经具备：

- 本地 Web UI 和 CLI。
- Ollama 实时对话。
- 长期目标和个人任务清单。
- 模型通过 Tool 查询和更新目标/任务。
- 每日摘要、Evidence 和启动补偿。
- 候选记忆审核和正式长期记忆。
- 周回顾。
- 提醒设置和数据库备份。
- 分层架构、权限和审计。
- 一键启动脚本。
- 84 项自动化测试。
- GitHub 仓库和草稿 PR。

项目已经从“可生成代码的 MVP 概念”进入“可以持续本地自用验证”的阶段。

## 十六、仍然存在的边界

- 本地模型速度依赖硬件，尚无流式输出。
- Web 服务只监听本机，没有登录、HTTPS 或公网部署。
- 超长单日聊天尚未分块分析。
- 跨午夜聊天和日报缺少完整会话锁。
- 候选记忆编辑和复杂冲突处理仍主要依赖 CLI。
- HTTP API 尚缺完整自动化契约测试。
- 真实模型质量缺少长期离线样本集。
- 尚未经过 30 天连续真实使用验证。

## 十七、下一阶段建议

建议按以下顺序继续：

1. 合并并标记当前 GitHub PR 为可评审状态。
2. 增加隔离数据库下的 HTTP API 集成测试。
3. 增加聊天流式输出或阶段性进度反馈。
4. 完成跨午夜会话锁和超长聊天分块分析。
5. 持续使用 30 天，记录真实失败、误判和记忆质量。
6. 用真实数据重新评估“主动教练”是否比普通任务工具更有价值。
7. 如果未来需要他人使用，再设计认证、数据隔离和安全部署。

## 结语

Personal Agent 的演进不是一条直线。它从 Telegram Bot 开始，经过邮件
备选、本地控制台、外部模型、本地模型、CLI、Web UI，再进入 Tool 真执行和
可追溯 Memory。

每次技术转向都不是为了追求更多功能，而是在回答同一个问题：

> 怎样让一个围绕个人目标、行动和反思的 AI 助手，真正稳定地在日常生活中
> 使用，而不只是停留在演示和模型回复里？

当前版本已经给出了一个可运行的本地答案。接下来最重要的不是继续堆叠页面，
而是长期使用、记录真实问题，并让系统在可靠性、记忆质量和行动闭环上继续
成熟。
