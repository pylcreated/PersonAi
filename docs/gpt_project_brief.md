## 二、项目概述

### 1. 项目定位

这是一个运行在 Windows 个人电脑上的本地实时对话式目标管理助手。

用户可以像聊天一样持续表达当天的进展、困难、情绪和想法。系统保存当天用户与助手的消息，并在次日自动生成结构化分析。分析成功保存后，系统自动删除前一天的全部原始聊天，只长期保留每日摘要、长期目标和任务。

项目强调：

- 本地运行。
- 单用户。
- 隐私优先。
- 免费模型。
- 实时对话。
- 原始聊天短期保留。
- 每日结构化总结。
- 长期目标和任务作为行动背景。

### 2. 当前阶段

项目已经完成最小可用实现（MVP），核心链路可以运行：

```text
用户输入普通文字
       ↓
保存用户消息
       ↓
加载当天聊天、目标、任务和最近摘要
       ↓
调用本地 Ollama 模型
       ↓
保存并显示助手回复
       ↓
次日 00:05 分析前一天聊天
       ↓
验证结构化 JSON
       ↓
在同一事务内：
保存每日分析 + 删除前一天原始聊天
```

## 三、产品设计

### 1. 三层记忆模型

项目当前采用三层信息结构。

#### 短期记忆

当天完整聊天记录，包括：

- 用户消息。
- 助手回复。
- 消息时间。
- 可选目标和任务关联。

短期记忆只用于当天实时对话和次日分析。

#### 中期记忆

每天生成一份结构化分析，包括：

- 当日总结。
- 进展。
- 阻碍。
- 行为或思维模式。
- 情绪或状态。
- 下一步行动。

原始聊天删除后，每日分析继续保留。

#### 长期记忆

长期保存：

- 长期目标。
- 每周任务。
- 每日分析。
- 经用户确认的个人资料、偏好、目标、项目、技能和经验。

每日分析只能创建待审核候选，不能直接写入正式长期记忆。用户可以查看、
编辑、接受或拒绝候选；只有确认且处于 `active` 状态的记忆能按需进入
聊天上下文。接受前会进行保守冲突检测，系统不会自动覆盖旧记忆。

### 2. 原始聊天保留策略

原始聊天按照北京时间自然日划分，而不是按照滚动 24 小时计算。

例如：

- 7 月 23 日的消息属于 `2026-07-23`。
- 7 月 24 日 `00:05` 分析 7 月 23 日消息。
- 分析结果校验并保存成功后，删除 7 月 23 日会话及全部消息。
- 7 月 24 日新产生的消息不受影响。

### 3. 删除安全规则

系统不会在分析开始前删除聊天。

删除顺序：

1. 读取前一天聊天。
2. 在数据库事务外调用模型。
3. 解析模型 JSON。
4. 验证字段和数据类型。
5. 开启短数据库事务。
6. 保存每日分析。
7. 删除对应每日会话。
8. 通过外键级联删除消息。
9. 提交事务。

如果模型调用、JSON 解析、字段验证或数据库写入失败：

- 不删除原始聊天。
- 会话状态改为 `failed`。
- 保存最近一次错误。
- 每 30 分钟自动重试。
- 程序下次启动时补做。

因此，在失败情况下原始聊天可能暂时保存超过一天。这是为了避免摘要尚未生成时直接丢失数据。

## 四、当前功能

### 1. 实时聊天

用户在主界面直接输入普通文字，系统会：

1. 获取或创建当天会话。
2. 保存用户消息。
3. 构造实时聊天上下文。
4. 调用本地模型。
5. 保存助手回复。
6. 输出回复。

不再要求用户使用固定的表格式复盘，也不需要输入 `/done`。

### 2. 实时上下文

每次实时回复会使用：

- 当前日期。
- 活跃长期目标。
- 本周任务及完成状态。
- 最近 7 天每日摘要。
- 今天最近 50 条聊天。

当天聊天文本目前限制在约 12,000 个字符以内，超出后保留较新的部分。

### 3. 每日分析

每天 `00:05` 分析所有早于今天、仍然保留的会话。

要求模型返回：

```json
{
  "summary": "当日总体总结",
  "progress": ["进展一", "进展二"],
  "obstacles": ["阻碍一"],
  "patterns": ["观察到的模式"],
  "mood": "当日状态",
  "next_actions": ["下一步行动"]
}
```

程序验证：

- 返回内容必须能够解析为 JSON。
- 根对象必须是字典。
- `summary`、`mood` 必须是非空字符串。
- 其余四个字段必须是字符串数组。
- 无法确定的信息应为空数组或“信息不足，无法进一步判断”。

### 4. 启动补偿

本地程序不保证凌晨一直运行。

每次启动时，系统会查询所有早于今天、仍存在原始消息的会话，并按日期依次补做分析。分析成功的会话会被清理，失败的会话保留。

### 5. 失败重试

程序运行期间，每 30 分钟检查一次历史未完成分析。

目前的处理特点：

- 如果最早一天失败，本轮处理会停止。
- 下一次重试仍从最早一天开始。
- 成功后继续处理后续日期。

### 6. 长期目标

支持：

- 首次运行创建多个目标。
- 查看活跃目标和目标 ID。
- 任务关联到指定目标。

命令：

```text
/goals
```

暂不支持目标重命名、停用、恢复和删除。

### 7. 每周任务

支持：

```text
/tasks
/task-add 目标ID 任务内容
/task-done 任务ID
/task-reopen 任务ID
```

每周任务按照周一日期归档，可标记完成或重新打开。

### 8. 每日分析查询

```text
/today
/daily
/daily 2026-07-23
```

- `/today` 查看今天仍然保留的原始聊天。
- `/daily` 查看昨天的每日分析。
- `/daily 日期` 查看指定日期的每日分析。

已删除的历史原始聊天无法查看，只能查看每日分析。

### 9. 每周报告

```text
/weekly
```

周报会读取：

- 本周每日分析。
- 本周任务。
- 为兼容旧版本而保留的历史复盘记录。

每日原始聊天不会用于周报，因为它们在每日分析完成后已经删除。

### 10. 定时提醒

支持：

- 每天在用户设置时间输出复盘提醒。
- 每周日在设置时间生成周报。
- 每天 `00:05` 生成每日分析。
- 每 30 分钟重试失败分析。
- 修改提醒时间后立即重新注册调度。

程序必须保持运行，普通提醒才能按时发生；如果程序关闭，每日分析会在下次启动时补做。

## 五、本地模型

### 1. Ollama

当前项目已经从付费 DeepSeek API 切换到本地 Ollama。

本机配置：

```text
Ollama 客户端：0.32.1
模型：gemma3:12b
模型文件：约 8.1 GB
运行占用：约 8.9 GB
上下文：4096 tokens
保持热加载：10 分钟
```

本机硬件：

```text
系统内存：约 15.8 GB
显卡：NVIDIA GeForce RTX 4060 Laptop GPU
推理分配：约 39% CPU / 61% GPU
```

已进行真实调用验证，模型成功返回：

```text
本地模型连接成功
```

首次加载耗时接近一分钟，后续热加载状态下通常会更快。

### 2. Ollama 调用方式

项目调用：

```text
POST http://127.0.0.1:11434/api/chat
```

请求包含：

- `model=gemma3:12b`
- `stream=false`
- `keep_alive=10m`
- `temperature=0.3`
- `num_ctx=4096`
- 普通回复最大约 300 tokens
- JSON 分析最大约 600 tokens

每日分析时增加：

```json
{
  "format": "json"
}
```

### 3. 当前环境配置

```dotenv
LLM_PROVIDER=ollama
LLM_MODEL_NAME=gemma3:12b
OLLAMA_BASE_URL=http://127.0.0.1:11434
OPENAI_MOCK_MODE=false
```

Ollama 不需要 API Key。

### 4. Mock 模式

如果：

```dotenv
OPENAI_MOCK_MODE=true
```

项目不会调用任何外部或本地模型，而是：

- 实时聊天返回确定性的占位回复。
- 每日分析只整理真实用户消息。
- 周报只使用数据库事实。

Mock 模式主要用于自动化测试。

## 八、数据安全和隐私

当前策略：

- 原始聊天默认只保存在本地 SQLite。
- 使用本机 Ollama 时，聊天不会发送给云端模型。
- 每日分析完成后删除前一天原始聊天。
- 删除操作与摘要保存处于同一事务。
- 分析失败时不删除。
- `.env` 被 Git 忽略。
- `.env.example` 不包含真实密钥。
- 自动化测试使用 SQLite 共享内存数据库。

仍未实现：

- 数据库自动备份。
- 每日分析导出。
- 数据库迁移版本。
- 用户主动删除指定每日分析。
- 加密数据库。
- 分析前人工确认。

## 十一、当前已知问题

### 1. 本地模型速度

`gemma3:12b` 能够运行，但首次加载接近一分钟。对于“实时对话”，等待时间可能偏长。

待评估：

- 是否换用较小的 4B 模型。
- 是否为实时聊天和每日分析使用不同模型。
- 是否需要流式输出。
- 是否需要缩短提示词。

### 2. 无流式输出

项目当前使用：

```json
{
  "stream": false
}
```

用户必须等待完整回复生成后才能看到结果。

### 3. 单日超长聊天

实时对话只保留最近约 12,000 个字符作为模型上下文，但每日分析会一次性提交当天全部消息。

如果当天聊天很多，可能出现：

- 超出模型上下文。
- 早期消息被模型忽略。
- 分析时间过长。
- JSON 输出截断。

当前尚未实现分块摘要。

### 4. 每日分析内容质量

每日分析现在会校验 progress、obstacles、next_actions 的 Evidence：

- message_id 必须属于当天真实用户消息。
- quote 必须逐字来自原消息。
- Evidence 与日报、候选和聊天清理处于同一事务。

仍未自动验证：

- 是否遗漏重要事实。
- 总结是否遗漏了未被模型选择的重要事实。
- 下一步行动是否足够具体。
- 同一内容是否重复。
- 情绪判断是否合理。

### 5. Ollama 服务依赖

如果 Ollama 没有启动：

- 用户消息已经保存。
- 助手回复失败。
- 用户会看到连接错误。
- 消息会保留，但当前没有独立的“补生成助手回复”机制。

### 6. 凌晨并发

如果用户恰好在 `00:05` 对前一天会话进行最后一轮模型调用，分析任务可能同时读取或删除该会话。

当前没有针对“正在生成回复”的会话级锁。

### 7. 失败日期阻塞后续日期

历史分析按日期顺序处理。如果最早日期持续失败，后续日期暂时不会处理。

### 8. 数据库迁移

当前已有三个原子 migration，覆盖初始结构、日报 Evidence 和 Memory
Provenance；启动时自动升级，失败回滚且可重试。

### 9. 长期摘要增长

实时对话只加载最近 7 天日报，因此历史摘要不会无限进入上下文，但目前还没有月度或长期压缩机制。

### 10. 分层架构已经完成

原有的根目录入口和兼容门面已经完成迁移：

- `personal_agent/__main__.py` 是唯一正式启动入口。
- 旧兼容代码暂存于 `legacy/`，正式源码不再依赖。
- `Agent` 只依赖 `LLMClient` 和 `ConversationMemory`。
- Ollama、OpenAI 兼容接口和通用 HTTP 模型位于独立 `llm/`。
- 日报和周报位于独立 `analysis/`。
- SQLite 位于 `memory/`，业务通过 `AgentRepository` 使用。
- CLI 位于 `interfaces/`，调度位于 `application/`。
- `bootstrap.py` 是唯一选择具体实现的位置。
- `tools/` 和 `security/` 已建立接口，权限默认拒绝。
- 架构测试会阻止核心层重新依赖具体适配器。

完整依赖规则见 `architecture.md`。
